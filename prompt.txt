You are an expert full-stack Django engineer and scientific-visualization developer working **inside an existing GitHub Codespaces repository**.

Your task is to extend the existing Django application with a **scalable, interactive spatial transcriptomics data viewer** inspired by the functionality and general interaction patterns of STOmics and HESTA.

## Non-negotiable constraints

* **Do not create a second Django project.**
* **Do not replace the existing architecture.**
* **Do not break existing routes, APIs, tests, provenance functionality, Docker configuration, or database behavior.**
* **Do not make destructive changes.**
* **Do not fabricate biological data or annotations.**
* **Do not load large expression matrices into MySQL or the browser unnecessarily.**
* **Do not render millions of spatial points as individual DOM elements.**
* **Do not hardcode dataset-specific filesystem paths or frontend dataset definitions.**
* **Reuse existing dependencies and architectural patterns whenever practical.**
* **Do not add a dependency until you have inspected the repository and determined that it is necessary.**

# 10. Large Scientific Data

The architecture must support datasets containing approximately:

```text
100,000+
1,000,000+
10,000,000+
```

spatial bins/points.

Never send a complete large expression matrix to the browser.

Never implement an endpoint equivalent to:

```python
return JsonResponse(entire_expression_matrix)
```

Instead use targeted requests.

For example:

```text
GET /api/spatial/<dataset_id>/metadata/
GET /api/spatial/<dataset_id>/layers/
GET /api/spatial/<dataset_id>/coordinates/
GET /api/spatial/<dataset_id>/expression/?gene=TP53
GET /api/spatial/<dataset_id>/clusters/
GET /api/spatial/<dataset_id>/umap/
GET /api/spatial/<dataset_id>/cells/
```

Prefer viewport-aware filtering:

```text
?xmin=...
&xmax=...
&ymin=...
&ymax=...
```

For example:

```text
/api/spatial/<dataset_id>/expression/?gene=TP53&xmin=...&xmax=...&ymin=...&ymax=...
```

Also consider:

* downsampling
* server-side filtering
* pagination
* caching
* compressed responses
* lazy loading
* multi-resolution data.

The API must protect itself against unreasonably large requests.
